# KNITPLAN

Code, workloads and result data for the paper **"KNITPLAN: Support-Aware Query Planning for Circuit-Cutting
Reconstruction"** (Jiachen Shen, Hui Zhong). Archived version: [doi:10.5281/zenodo.24122016](https://doi.org/10.5281/zenodo.24122016).

KNITPLAN answers marginal, group-by, bin and point queries over the shot tables of a cut quantum circuit. It treats
reconstruction as a sum-product (join-aggregate) query: it pushes aggregation and selection below the configuration
merge, computes the support of each cut elimination from cut-indexed statistics, and chooses join order and per-node
sparse/dense format under a planning-time and memory budget. It returns CutQC's finite-shot estimator within a
tolerance computed from the inputs.

## Layout

| Path | Contents |
|---|---|
| `knitplan/` | the system: cut schemes (`cutting.py`), shot tables (`shots.py`), factor build, operators, executor and the rounding tolerance (`engine.py`), statistics, cost model and planner (`planner.py`), point batches (`points.py`) |
| `bench/` | workload generation, shot generation, the compared systems (`systems.py`, `galley_runner.jl`, `qcut_runner.py`), the end-to-end harness (`m1_time.py`), result summaries and paper figures |
| `derisk/` | the planner study (`e1_time.py`), sparsity measurements (`d1_*`, `e1_support.py`), equivalence checks (`d6_equivalence.py`, `t0_*`), Galley comparison (`e1_galley_*`); results in `derisk/results/` |
| `derisk/data/`, `derisk/noise_model_readout_2026-11-07.json` | the archived `ibm_cleveland` noise model, device properties and readout snapshot (2026-11-07) used for noisy shots |
| `data/m1/` | inputs for offline reproduction: per-unit records of the end-to-end comparison (`pilot/`), the shot tables and batch metadata of the 12 device instances (`shots/`, `qpu/batch.json`) |
| `tools/test_*.py` | unit and equivalence tests |
| `env/ENVIRONMENT.md`, `requirements.txt` | the exact software environment |

## Setup

1. Python 3.13 and `pip install -r requirements.txt`.
2. External systems (versions and commits in `env/ENVIRONMENT.md`): CutQC at commit `cda68c7` (cloned, on the Python
   path), QCut 2.4.0 in a separate Python environment (its interpreter path is the constant `QCUT_PY` in
   `bench/systems.py`), Julia 1.13 with Galley.jl 0.2.2 and Finch 2.1.1 (the Julia environment path is `GALLEY_ENV` in
   `bench/systems.py`), and DuckDB (Python package).
3. Data root: scripts read and write under `D:/runs/knitplan` unless the environment variable `KNITPLAN_RUNS` is set.
   For the offline reproductions below, set `KNITPLAN_RUNS=<this repository>/data`.

## Paper results and how to reproduce them

Offline from archived results (no external systems needed):

| Paper element | Command | Input |
|---|---|---|
| Fig. 1 and the evaluation figures (rule distribution, planning overhead, end-to-end per query, factor density, cost model) | `python bench/paper_figs.py` (functions `fig1`, `fig_rules`, `fig_overhead`, `fig_e2e`, `fig_density`, `fig_costmodel`) | `derisk/results/E1/T`, `derisk/results/D1`, `derisk/results/M1/pilot_summary.json` |
| Fixed rules vs. best plan (Table I) and the planner-study numbers | `python derisk/e1_summary.py` | `derisk/results/E1/T/*.json` |
| End-to-end comparison (Table II) | `KNITPLAN_RUNS=data python bench/m1_pilot_summary.py` | `data/m1/pilot/*.json` |
| Device table (Table III) | `KNITPLAN_RUNS=data python bench/qpu_support.py`, then `python bench/device_table.py` | `data/m1/shots`, `data/m1/qpu/batch.json` |
| Equivalence numbers | `derisk/results/D6_certified.json` (generated by `python derisk/d6_equivalence.py`) | |
| Galley comparison | `derisk/results/E1/G.json` (generated by `derisk/e1_galley_export.py` and `derisk/e1_galley_compare.py`) | |

Fig. 2 is an architecture diagram (no data).

From scratch (requires the external systems and, for new device data, IBM Quantum access):

1. Tests: `python tools/test_engine.py`, `tools/test_planner.py`, `tools/test_join_stat.py`, `tools/test_tau_cert.py`,
   and `tools/test_systems.py` (the last one needs the instances and shots of steps 2 and 3).
2. Instances: `python bench/build_pilot.py` for the pilot instances; `python bench/e1_probe.py` and then
   `python bench/e1_build.py` for the planner-study workload; for the main workload
   `python bench/m1_probe.py` (MQT Bench families), `python bench/m1_probe.py adder,supremacy_d4,supremacy,hwea,bv,aqft,regular,hetero`
   (CutQC families) and then `python bench/m1_build.py`. The probes search cut schemes and write the candidate lists that the
   build scripts read; the build scripts write the instances under the data root. The frozen manifests are
   `bench/*MANIFEST.json`.
3. Shots: `python bench/e1_shots.py --exp e1` and `--exp m1` (ideal shots by state vector or MPS; noisy shots from the
   archived noise model and readout snapshot in `derisk/`).
4. Planner study: `python derisk/e1_time.py run` (timed; run pinned to one core on an otherwise idle machine).
5. End-to-end comparison: `python bench/m1_time.py prep`, then per instance, with the settings used in the paper,
   `M1_PILOT=1 M1_PILOT_CAP=120 M1_MEMCAP_GIB=16 M1_SYSTEMS=knitplan,default_rule,dense_pushdown,cutqc_dd,li_sparse,duckdb_pushdown,qcut,galley python bench/m1_time.py run <instance>`
   (one warm-up and one measured run per query and system; the GHZ controls used `M1_PILOT_CAP=600`).
6. Device runs: `python bench/qpu_batch.py plan|submit|fetch` (IBM Quantum account required).
